# 연동 팩과 대화형 초기 설정 구현 준비안

상태: 2026-09-10 조사·준비 이후, 2026-09-11 승인된 문답형 설정과 호스트 처리 구현.
6개 live adapter, 범용 설치 권한, 공통 쓰기 계약은 아직 구현하지 않았다.
기존 Go + SQLite, 사람의 활성 룰셋 소유권, 실행기 교체 가능성을 유지한다.

2026-09-11 사용자가 요청한 [실제 프로세스·설치 진입 점검](../validation/INTEGRATION_RUNTIME_ATTEMPT_2026-09-11.md)에서
worker의 자연어 입력 처리와 `chat` 진입점이 없고, 실행 중 `gmail connect`도
writer 잠금으로 막히는 것을 확인했다. AI 설치 대화와 6개 개별 인증은 검증하지
못했다. IN-01·IN-02의 우선 완료 증거는 worker를 켜 둔 상태에서 자연어 요청,
추가 질문, 인증 인계, 호스트 연결 결과 확인이 이어지는 실제 대화 기록이다.
이 점검은 미구현 권한 계약이나 전체 adapter 구현을 승인·완료 처리하지 않는다.

그 뒤 사용자가 “설정 전용 대화하고 처리하는 프로세스까지 구동”을 승인했다.
`chat`과 `setup serve`, 기존 worker 관리 채널의 제한된 `setup.*` 요청을 구현했다.
설정 팩 로컬 설치 및 Gmail 신규 연결/기존 계정 확인만 실행한다. 현재 대화는 LLM
호출 없는 고정 문답형이다. [호스트 계약](../contracts/setup-v1.md)과
[실행 증거](../validation/SETUP_CHAT_2026-09-11.md)가 앞선 진입점 부재 기록을 보완한다.

## 범위와 기본 판단

기본 지원 목표는 Drive(Docs/Sheets), Figma, GitHub, Slack, Telegram, Gmail이다.
읽기 전용 제품으로 고정하지 않는다. 서비스별 읽기·작성·수정·전송을 카탈로그에
표현하고 사용자가 원하는 기능을 선택하게 한다. 새 기능이 기존 메일/Jira
읽기 경계를 자동으로 넓히지는 않는다.

권고안은 **하나의 버전 관리된 연동 팩을 AI 설정 도우미와 고정 설치 helper가
공유하는 방식**이다. AI는 질문·경로 선택·오류 설명을 맡고, 호스트가 승인된
설치 단계와 OAuth·비밀 저장·범위 검증을 수행한다. helper가 없는 외부 plugin은
사용자의 기존 AI 도구에 설치하도록 안내할 수 있으나 Chun-su 검증 완료로 표시하지 않는다.

## 두 설치 방식의 실행 경계

| 구분 | AI 안내/보조 방식 | 고정 helper 방식 |
|---|---|---|
| 공통 입력 | 선택 서비스·목적·기존 연결·지원 환경·매뉴얼 버전 | 동일 |
| 계획 | AI가 설치 팩의 허용 경로를 선택하고 질문 | 옵션/대화형 입력으로 동일 경로 선택 |
| 설치 | 설정 전용 세션이 승인된 helper 호출을 요청 | 로컬 호스트가 같은 helper 호출 |
| 인증 | browser/로컬 masked 입력으로 인계 | 동일 |
| 검증 | 호스트가 실제 결과 확인 후 상태 보고 | 동일 |
| 차이 | 문서 해석과 오류 설명의 유연성 | 반복 설치의 재현성 |

현재 보고 실행기는 사용자 config/host skill을 무시하고 shell·추가 MCP 등을
차단한다(`internal/executor/codex.go`). 이 제한을 풀어서 installer를 실행하게
하는 것은 기존 격리 증거를 무효화한다. 설정용 session/adapter 또는 호스트
설치 명령을 따로 정의해야 한다. 이번에는 위 제한된 호스트 설정 계약을 구현했으며,
외부 실행기의 임의 설치·shell 허용과 새로운 서비스 권한은 여전히 별도 결정이다.

외부 실행기에 연결된 OAuth를 호스트가 읽을 수 있는 것으로 가정하지 않는다.
인증 저장소 소유권·중계 지원·제공자의 client 등록 제한을 확인한다. 특히 Figma
지원 client를 흉내 내서 접속하거나 다른 앱의 OAuth secret을 복사하지 않는다.

## 연동 팩에 포함할 항목

현재 제공하는 팩은 `setup-skills/connect-services/`이며, 공통 Skill과 6개
매뉴얼, 준비 도구가 있다. `catalog.json`은 준비 도구의 표시/질문 인덱스일 뿐
보안 정책·실행 권한 계약이 아니다. 향후 runtime 팩은 아래 정보를 검토 후 갖춘다.

| 항목 | 목적 |
|---|---|
| 제공자·출처·지원 환경 | 공식 API, 공식/커뮤니티 CLI/MCP, 라이선스, 호환 버전 구별 |
| 의존성과 설치 내용 | 파일/패키지/서비스 변경 목록, 고정 artifact·해시, 검증·제거 방법 |
| 사용자 질문과 인증 경로 | 계정 유형, 조직 승인, callback/client 유형, 필요한 권한 설명 |
| 기능 목록 | 공개 도구 표면과 호스트 허용 동작의 연결, 리소스별 제한 |
| 자격증명 소유권 | Keychain 등 호스트 저장, 실행기는 reference가 아닌 도구 권한만 받음 |
| 검증 절차 | 연결·범위·거부·기능·골든 확인, partial/unknown 보존 |
| 복구와 해제 | 중단 지점 재개, reauth, 변경분 rollback, revoke, 데이터 보존 구별 |

제7의 서비스를 추가할 때 매뉴얼과 catalog 항목만으로 **설정 안내**는 확장할 수
있다. 실제 기능에는 adapter·권한·증거 변환이 필요하다. MCP 호환성만으로
리소스 제한·재시도·쓰기 안전성까지 자동 확보된다고 하지 않는다.

## 전체 기능을 지원하면서 범위를 제한하는 방법

기능 표면은 서비스별로 준비하고 사용 권한은 작업 단위로 좁힌다.

| 분류 | 예 | 호스트가 확인할 내용 |
|---|---|---|
| 읽기 | Docs 내용, Sheet 범위, repo diff, Slack thread, Gmail 본문 | 계정/리소스·범위·분량·증거 |
| 작성 | 새 Doc, Sheet 행, issue, PR, 메일 draft | 목적지·내용·신규 리소스 소유권, 중복 생성 |
| 수정·전송 | 문서 치환, PR 코멘트, Slack/Telegram 답장, 메일 send | 기존 승인 범위, 대상·최종 내용, 충돌/중복·전송 결과 |
| 삭제·권한·관리 | 파일 삭제/공유 변경, merge, channel 초대 | 별도 명시적 계약과 사용자 결정, 복구 가능성 |

“초안”도 원격 Gmail draft나 GitHub PR로 저장하면 외부 쓰기다. 로컬 초안과
구별한다. Sheets의 `drive.file`처럼 제공자 권한이 좁은 파일 범위의 쓰기까지
포함할 수 있으므로 실제 읽기 전용 실행은 호스트 도구 제한으로 확인한다.

Slack/Telegram 입력 채널과 읽기 도구는 분리한다. 인증된 발신자라도 원문에
포함된 다른 사람의 말은 지시 권한이 아니다. 사용자 ID·workspace/chat ID를
사용자 설정과 연결하고, 봇 응답·이벤트 중복이 새 작업을 재귀 생성하지 않게 한다.
전송 결과 불명확 시 재전송으로 성공을 추정하지 않고 provider 결과 조회나
사람 확인으로 복구한다.

## 연결 상태와 룰셋 검증 표시

다음 표는 UX 의미 제안이며 DB enum이나 외부 API로 확정하지 않는다.

| 표시 | 필요한 증거 |
|---|---|
| 준비됨 | 지원 매뉴얼·의존성 경로 확인 |
| 로그인 필요 / 관리자 승인 필요 | 실패 원인을 계정 범위에서 식별 |
| 외부 도구 연결됨 | 제공자 identity와 실제 제한 리소스 호출 성공 |
| Chun-su에서 사용 가능 | 호스트 adapter·도구 목록·범위와 비밀 격리 검증 |
| 이 룰셋으로 검증됨 | 아래 조합과 연결된 독립 평가·거부 시나리오 근거 |
| 부분 지원 / 재검증 필요 | 쓰기 미지원, 권한/버전/도구 표면 변경, 누락 근거 |

검증 대상으로 묶을 조합: **룰셋/Skill 해시 + 실행기 버전/모델 + connector와
설치 artifact 버전 + API/tool 스키마 해시 + 계정 권한·리소스 정책 + case/rubric/
평가자 버전**. 단순 “연결 성공”과 구별한다. gws의 동적 API 발견과 remote MCP의
도구 갱신 때문에 바이너리 버전만 고정해서는 충분하지 않다. 새 도구/권한은
기존 검증 표시에 조용히 편입하지 않는 방향이다.

골든 기대값은 실행 패키지에서 제외하고, connector 검증과 의미 평가를 나눈다.
예: 특정 sheet를 읽었다는 증거는 값 해석의 정답을 의미하지 않는다. 평가자는
보존 원문과 결과·기대값을 읽을 수 있지만 connector 인증과 활성화 권한은 없다.
위 조건에서의 검증 성공만 표시하며 모든 미래 데이터에 대한 보장은 하지 않는다.

## 개발 작업 단위와 완료 증거

IN 번호는 이번 확장 준비의 로컬 작업 식별자이며 기존 Phase 전체를 완료 처리하지 않는다.

| ID / 연결 작업 | 상태 | 산출물·완료 증거 |
|---|---|---|
| IN-00 / P7-01·03 준비 | complete (preparation only) | 공식 조사, 6개 설치 매뉴얼, 공통 Skill, 오프라인 선택 도구. 아래 검증 기록 참조 |
| IN-01 / P0-05·06, P7-03 | implemented (bounded) | 고정 문답형 설정, 별도 호스트/worker 관리 요청, 버전별 자료 설치와 작업 상태. 보고 실행기 변경 없음. AI 자유대화·범용 installer 제외 |
| IN-02 / P4-01·02, P7-03 | partial | 새 연결 OAuth 경로와 기존 연결 확인 구현, 실제 기존 계정 확인 성공. 새 브라우저 승인·만료 후 in-place 복구·신규 계정 오인 시나리오의 live 검증은 미완료 |
| IN-03 / P3-02·06 | proposed | 연동 버전/도구 표면과 검증 근거 연결. 변경 시 재검증 표시, 미충족 필수 근거로 활성화하지 않음 |
| IN-04 / 확장 | proposed | Drive Docs/Sheets와 GitHub 호스트 adapter. 지정 원문 읽기, 범위 밖 거부, 선택된 작성 기능의 결과 재조회 |
| IN-05 / 확장 | proposed | Telegram polling·페어링·대화/알림. 타 사용자 차단, 중복 update, 불명확한 send 결과 처리 |
| IN-06 / 확장 | proposed | Slack 내부 앱·Socket Mode·채널별 권한. 이벤트와 읽기 권한 검증, 조직 정책/토큰 유형 한계 기록 |
| IN-07 / 확장 | proposed | Figma REST 읽기와 지원 MCP 편의 경로. client 자격, file/node 범위, 도구별 쓰기 가능성 검증 |
| IN-08 / P7-02·04 | proposed | 새 환경 설치·업데이트·중단 복구·제거. 기존 개인 설정을 덮어쓰지 않고 설치 변경분만 복귀 |

쓰기/전송 구현 시나리오는 지정된 검증용 목적지와 구체적인 사용자 승인 아래
진행한다. 새 테스트 코드는 별도 요청 없이는 만들지 않고 기존 테스트와 수동
시나리오의 증거를 남긴다. 반복 운영·외부 메시지는 이번 조사에서 실행하지 않았다.

## 구현 전에 남은 결정

1. 설정 도우미가 호스트 helper를 요청하는 권고 경로와 외부 실행기 직접 설치의
   허용 범위. 현재 제한된 보고 실행기를 그대로 installer로 쓸 수는 없다.
2. 개인용 BYO 앱/토큰부터 시작할지, 배포자 관리 Google OAuth·GitHub/Slack 앱을
   먼저 준비할지. 원클릭 로그인에는 제공자 앱 등록·검토가 선행되어야 한다.
3. 각 서비스의 첫 쓰기 기능과 승인 범위. 모든 API를 처음부터 무제한 노출하지 않고
   기능은 넓게 목록화하되 검증된 단위부터 제공하는 안을 권고한다.

제한된 문답형 호스트 경로는 위 후속 승인으로 구현했다. 배포자 관리 앱, 외부 실행기
직접 설치, 새 쓰기 권한은 이번 구현에서 정하지 않았다. DB 마이그레이션은 없다.

검증 결과는 [IN-00 준비 검증](../validation/INTEGRATION_PREPARATION_2026-09-10.md)에 기록한다.
