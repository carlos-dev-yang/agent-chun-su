## 출시 판단에 남은 공백

1. **비교 가능성과 채택 적합성이 분리되어 있지만 후자의 규칙이 부족하다.**
   `Compare`는 조건 일치와 평가 존재 등을 확인한다. 의미 평가가 fail이더라도
   같은 조건이면 비교 가능할 수 있다. `Decide(adopt)`는 해당 baseline/candidate,
   `Comparable`, human 요청을 확인하지만, 품질 퇴행·필수 기준의 통과·
   `Proposal.RequiredChecks` 완료를 검사하지 않는다. 이는 코드 경로의 확인이며
   실패 후보를 실제로 채택하는 실험은 하지 않았다. 현재 동작을 우회 취약점으로
   단정하기보다, D10에서 확정할 출시 정책이 아직 연결되지 않은 상태로 본다.

2. **골든 기준의 신뢰 수준과 독립성이 채택 조건에 연결되지 않았다.**
   case/rubric 검토 상태와 평가 한계는 저장되지만 `Compare`/`Decide`에서
   검토 상태를 필수 조건으로 쓰거나 평가의 모든 한계를 집계하지 않는다.
   공개 메일 rubric은 draft이며 사례들은 검증용이다. 실행 전에 고정했다는
   사실만으로 미노출 확인셋이 되지 않는다. 튜닝·회귀·독립 확인 용도와 노출
   이력을 출시 근거에서 구별할 필요가 있다.

3. **평가자 실행 격리는 아직 제품의 실행 경로가 아니다.**
   `pin-evaluator`는 Skill을 보존하고 이후 판단을 import한다. Skill 해시 검증은
   평가자가 실제로 그 지침과 한정된 자료만 사용했다는 실행 증거까지 만들지는
   않는다. 독립 평가 기록은 있으나 평가 패키지·권한·실행 이력을 일관되게
   만드는 자동 평가 실행 경로는 없다. `actor_kind=human` 역시 로컬 사용자
   명령의 선언이지 별도 신원 인증 체계가 아니므로 권한 경계의 증거와 구별한다.

4. **출시에 사용할 평가를 명시적으로 선택하는 연결이 약하다.**
   `InspectRun`은 현재 attempt 평가들을 수집하고 `Compare`는 각 목록의 첫
   평가를 규칙 비교에 사용한다. 비교에는 평가 내용이 포함되지만 평가 record ID를
   별도로 유지하지 않는다. 재평가·판정 불일치가 있을 때 어떤 평가 쌍을 채택
   근거로 선택했는지 명시하고, 이전 판단과 차이를 설명하는 보강이 필요하다.
