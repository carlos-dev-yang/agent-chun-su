## 1. 승인된 범위와 완료의 의미

이번 우선순위는 개발/코드 리뷰 기능 확대가 아니라 팀 업무의 약속, 진행, 배포,
근거 부족과 대응을 한 흐름에서 관리하는 것이다. 기존 mail/Jira 읽기 경계와
사람이 활성 제어를 소유하는 원칙은 유지한다. 기존 code-review는 삭제하지 않지만
새 기능·파일럿·실행 품질 검증의 대상에서 제외한다.

OPS-02는 기존 Go/SQLite schema 5, 한 데이터 홈의 단일 owner/controller,
저장 mail/Jira/Slack 입력으로 구현한다. 업무 기록은 실제 소유자가 입력한 로컬
사실을 저장할 수 있다. 실제 사내 원문을 외부 AI에 공개할 계약은 아직 없으므로
AI 보고는 명시적으로 선언한 공개 합성 scope와 원래 합성인 저장 입력만 허용한다.
새 RBAC, live Slack 수집, 외부 알림 발송, 사내/EC2 배치와 migration은 포함하지 않는다.

`implemented`, `tested`, `pending`을 구분한다. 합성 파일럿 통과는 팀 사용 권한,
상시 수집, 실제 호출 도달, 팀 유용성 또는 운영 준비 완료의 증거가 아니다.
실제 결과와 제한은 [OPS-02 검증 기록](../validation/OPS_02_LOCAL_2026-10-05.md)에 남긴다.

| 작업 | 산출물 | 현재 경계 |
|---|---|---|
| OPS-01 | 설치된 Codex CLI 호환성, 실제 FLOW 실행 근거를 기존 feedback/비교에 연결 | 별도 실행·평가 기록; 검증 실패도 그대로 보존 |
| OPS-02 | owner 업무/일정/릴리스 ledger, 저장 근거, AI 위험 보고, shadow incident/outbox | 로컬 구현; 합성 수용 검증 기록 참조 |
| OPS-03 | 사내 접속·공개 범위·사용자/수신 권한·연속 수집·실제 발송 | 미구현, 해당 외부 계약 확인 후 별도 승인 |

## 2. 상태와 책임

| 축 | 상태/판정 | 누가 변경하는가 |
|---|---|---|
| 업무 | `ready`, `inprogress`, `waiting`, `completed`, `cancelled` | 명시적 owner 명령 |
| 실행 | FLOW job/step/attempt/result | 기존 controller/실행 계층 |
| 관측 | 외부 Jira 상태, mail/Slack 버전·시간·누락 | 저장 입력 정규화; 내부 업무를 덮어쓰지 않음 |
| 위험 | P0–P3, 영향, 확신도, 조치, 출처 span | 실제 AI 보고 + host 구조/근거/계산 검증 |
| 대응 | `open`, `acknowledged`, `responding`, `resolved` 및 만료 snooze | owner 확인·대응 명령; 새 근거 위험은 재개 가능 |
| 전달 | `shadow_planned`, `shadow_blocked`, `suppressed` | 정책으로 로컬 계획만 작성; `sent` 없음 |

업무 생성은 `ready`이다. 진행/대기 전환은 기한을 바꾸지 않는다. 대기는 사유,
해소 책임자와 다음 확인 시각이 필수다. 완료는 지정된 source/span 근거 또는
명시적 owner 확인을 요구한다. 완료/취소 후 다시 시작할 때는 이유를 남기고
`ready`/`inprogress`로 재개한다. 모든 변이는 actor/reason/예상 revision이 필수다.
취소·제외·완료·incident 해결은 서로 다른 사실이다.

## 3. 저장 계약과 안전한 재시도

새 테이블 없이 기존 append-only record에 `kind=ops_event`를 추가한다.
scope 키는 검증된 team/project의 canonical JSON SHA-256이며 `ops:` 접두어를 가진다.
각 record는 version, scope, 연속 revision, 이전 record ID/digest, host 시각,
canonical 명령 digest와 명령을 보존한다. 데이터 홈의 private 권한과 기존 백업을 재사용한다.

`Command`는 `version`, `scope`, `operation_id`, `expected_revision`, `actor`,
`reason`, `action`, `entity_id`, typed `data`로 구성한다. 정확히 동일한 operation ID와
명령 재시도는 처음 receipt를 반환한다. 다른 명령에 같은 ID를 재사용하면 거부한다.
예상 revision 충돌은 자동 덮어쓰기/재시도가 아니라 최신 history 확인을 요구한다.
결과가 불명확하면 `ops receipt OPERATION_ID`를 확인하고 정확히 같은 명령만 재시도한다.

재생은 scope 전체를 DB에서 조회한다. 기본 1,000건 제한이나 조용한 history 절단을
사용하지 않는다. record digest, 연속 revision, 이전 digest, scope, 명령 hash,
operation 중복을 확인하고 모두 유효할 때만 상태를 반환한다. 총 재생 byte 한도는
기존 `limits.max_evidence_bytes`, 개별 record 한도는 `limits.max_artifact_bytes`이다.
초과·누락·변조는 fail closed이며, 새 event를 쓰기 전에 총 한도를 확인한다.
향후 compaction/migration은 이 첫 범위에 없고 별도 복구 계약이 필요하다.

| 모델 | 핵심 필드/불변식 |
|---|---|
| Settings | IANA timezone, 명시적 synthetic 선언; 기본 false |
| WorkItem | ID/title/owner/완료 기준/state, 최초/현재 due, evidence, waiting, 생성/변경 host 시각 |
| ScheduleRevision | 이전/새 due, actor/reason/host 시각/revision; 최초 약속은 불변 |
| ReleaseCycle | ID/service/environment, ready_by/deploy_by, 대상 변경 이력, deployment evidence |
| Commitment | work ID, included/excluded/carried, 사유/actor/revision/다음 cycle |
| Observation | 원래 형식, scope, 원본 bytes/digest, 수집 구간/coverage/gaps, 정규화 source versions |
| Assessment | 실제 FLOW job/validated artifact/input/Skill digest, ledger revision, 검증한 보고 |
| Incident | 결정적 identity, revision, evidence/severity fingerprint, 현재 판단/대응/확인/해결 근거 |
| Notification | incident/revision/수신자 dedup key, 적용 정책, mode/status/reason/시각; sender 없음 |

## 4. 일정과 배포: 미달성 사실을 숨기지 않는다

RFC3339 offset 시각을 입력하고 scope timezone을 표시한다. 휴일/근무일/유예 규칙을
임의 추정하지 않는다. 최초 due와 현재 승인 due의 초과, 일정 변경, 완료 시점의
최초/현재 지연을 각각 host가 계산한다. 재조정은 과거 약속을 지우지 않는다.

배포 readiness 마감과 deployment 마감은 별개다. 대상 목록은 추가/제외/이월
사유를 보존한다. 다음 주기 이월은 같은 service/environment, 더 늦은 deploy_by인
기존 cycle만 허용하며 원래 cycle과 다음 cycle을 하나의 event로 변경한다.

deployment는 work IDs, 정확한 environment, `deployed|not_deployed|unknown`,
증거가 확정하는 effective_at, source/span 또는 owner 근거로 기록한다.
host 기록 시각과 증거가 가리키는 시각을 구분한다. 같은 시각의 충돌 증거는 unknown이다.
보고 기준 시각보다 뒤의 증거를 현재 배포 사실로 사용하지 않는다.

| 상황 | 판정 |
|---|---|
| 대상 업무 미완료 | `work_incomplete` |
| 완료 + 정확한 환경 deployed 근거 | `complete` |
| 완료 + `not_deployed` 근거 | `deployment_not_done` |
| 완료 + 배포 근거 없음/unknown/충돌 | `deployment_unknown` — 확정 미배포가 아님 |
| 배포됨 + 내부 업무 미완료 | `deployed_unrecorded` |
| 승인 제외/다음 주기 이월 | `excluded` / `carried` |

## 5. 저장 입력과 공개 경계

기존 mail Snapshot과 Jira ReportInput을 그대로 받는다. Slack v1 envelope 예시는
[saved-slack.json](../../examples/team-ops/saved-slack.json)이다.

Slack envelope는 provider/version/scope/synthetic/workspace_id/allowed_channels,
captured_from/through/coverage/gaps/messages를 갖는다. 메시지는 ID/event ID/version,
channel/thread/source_at/kind/message text/content_status/URI를 갖는다.
범위 밖 채널, 잘못된 시각, 같은 ID/version의 다른 내용과 중복 원본은 거부한다.
수정·삭제 버전과 늦게 도착한 관측은 시간/버전을 보존한다. 삭제는 원문 없는
tombstone이고 근거 부족으로 드러난다. 수집 구간은 saved capture의 주장이지
실제 Slack 연속 감시 커서가 아니다.

원본 bytes는 event 안에 base64로 보존하고 원본 digest를 검증한다. 정규화 결과도
원본에서 다시 만들어 비교한다. mail/Jira content 버전은 projected content digest를
포함하므로 같은 updated_at의 메타데이터-only → 상세 복구를 새 근거로 보존한다.
source ID와 host 만든 line span ID를 AI에 제공한다. 원문 자유 인용의 정확성에
의존하지 않는다. scope 명칭은 공개 권한이나 팀 인증을 뜻하지 않는다.

scope synthetic 선언과 모든 저장 원본의 synthetic 선언이 함께 true일 때만
외부 AI 보고를 허용한다. 실제 저장 자료를 synthetic으로 바꾸거나 scope 이름으로
비공개 자료 공개 승인을 대신할 수 없다. generic `flow submit`도 host가 현재 ledger와
원본 provenance를 재구성하여 비교한다. 입력 scope와 정확히 같은 project Skill
namespace가 필수이며 다른 프로젝트/누락/common fallback은 거부한다.

## 6. 실제 보고와 재조정

`ops report`는 현재 scope 입력을 만들고 기존 FLOW에 저장한다. collect와 refine는
명시적 host 단계이며 span projection과 결정적 WorkStatus/ReleaseStatus를 만든다.
fake AI refine receipt는 없다. synthesis만 설치된 승인 Codex CLI와 고정한 Skill을
사용하는 실제 AI 실행이다. legacy gateway로 몰래 fallback하지 않는다.
설치된 CLI의 exact tool-free boundary가 지원되지 않으면 정확한 unavailable을 반환한다.

보고는 scope/revision/input digest/as_of와 host 상태 행을 그대로 유지한다.
AI는 영향·시급성·진행 중 대응·담당자·불확실성·권장 조치 및 source/span을 제시한다.
host는 schema, 모든 source의 disposition, target/인용 ID, 기계적 상태 및 시간 계산을
검증한다. `completed`는 보고의 근거 범위가 완전할 때만 사용하고 수집 공백, stale,
truncated/deleted 내용 또는 모델 한계가 있으면 `partial`로 보존한다.
이 보고 status는 업무 완료나 외부 전달 status가 아니다.

`ops reconcile JOB_ID`는 독립 InspectRun이 검증한 실제 AI audit/response/receipt,
호스트 단계 receipt, 고정 input/Skill/validated artifact와 현재 ledger revision을
재검사한 뒤 Assessment/Incident/Notification만 쓴다. 업무/기한/대상/배포는 바꾸지 않는다.
임의 `ops apply`/IPC로 assessment를 주입할 수 없다. 접수 AI의 team-ops delegation은
초기 owner CLI 범위에서 차단한다. ledger가 바뀌었으면 fresh 보고를 요청해야 한다.

## 7. 저소음 shadow 대응

P0/P1 immediate, P2 digest, P3 none은 명명된 기본 분류이지 실제 발송 구현이 아니다.
정책 JSON은 등급별 recipients/mode/cooldown_seconds/acknowledgment_seconds,
source_freshness_seconds와 P0 snooze 우회를 명시한다. 기본 recipients는 비어 있어 blocked이며,
임의 응답/호출 시간 수치를 코드가 정하지 않는다. 공개 예시 수신자는 demo label뿐이다.

같은 incident의 동일 근거/심각도는 새 호출 계획을 만들지 않는다. owner/확신도/영향/
권장 조치가 교정되면 현재 판단과 revision은 갱신하되 알림 wording만으로 중복 호출하지 않는다.
서로 다른 risk가 같은 effective incident에 링크되면 보고 적용 전체를 거부한다.
새 근거/등급 변화는 새 revision이고 해결된 incident도 재개할 수 있다.
등급 상승은 cooldown/snooze에 묶이지 않는다. P0 우회는 설정으로만 허용한다.

acknowledged는 resolved가 아니다. 해결은 근거가 필요하다. snooze는 미래 만료
시각을 가져야 한다. `ops outbox review`는 현재 snooze/정책/만료에 맞춰 새로운
shadow preview를 append하고 과거 계획은 보존한다. 같은 정책/status/reason의
반복 review는 새 계획을 만들지 않는다. 만료 후 재계획은 owner가 이 명령을
실행할 때만 이루어진다. 이 범위에는 background scheduler, 실제 재전송,
미확인 상향 호출 또는 provider exactly-once 보장이 없다.

## 8. 실행 결과에서 내부 Skill로 성장

별도 학습 플랫폼을 만들지 않는다. 정확한 프로젝트 Skill 구성과 FLOW 실행 결과를
기존 feedback/사례/후보/독립 평가/비교/사람 채택/rollback 흐름에 연결한다.
피드백은 missed incident/false positive/severity/owner/duplicate/grounding/usefulness를
근거와 함께 남길 수 있다. 실제 synth와 host refine를 구분한 실행 근거가 필요하다.
후보는 비활성이며 평가 실패·불충분 근거는 성공으로 정규화하지 않는다.
TEAM-08A scope는 명칭/선택 namespace이고 팀 사용자 권한/데이터 격리가 아니다.

실제 candidate→평가→채택 결과는 [OPS-01 FLOW feedback 안내](../setup/FLOW_FEEDBACK.md)와
[실행·평가 검증 기록](../validation/OPS01_FLOW_FEEDBACK_2026-10-05.md)을 따른다.
team-ops에서 그 전 과정을 통과했다고 이 구현만으로 주장하지 않는다.

## 9. 변경 소유권과 남은 외부 결정

domain은 `internal/ops`에 두고 runner/workgroup을 import하지 않는다.
`internal/cli/ops.go`, `internal/runner/ops.go`가 owner 명령과 실제 FLOW/feedback 검증을
연결한다. workgroup registry/새 adapter/내장 assets와 records kind만 확장했다.
OPS-01이 executor/feedback/stagedworkflow를 소유해 명시적 host refine와 실제 synth
근거를 통합한다. 같은 파일 동시 편집과 가짜 receipt를 피하고 독립 review를 수행한다.

실운영 전 필요 결정: 회사 저장 입력/보존·삭제 정책, 외부 AI 공개 승인/마스킹,
실제 Slack/Jira/mail 인증·접속/연속 수집 계약, 팀 사용자 식별·조회/전이/수신 권한,
당번/대체자/업무시간, provider 송신/조회/멱등성, 승인된 등급·응답·상향 시간,
관리형 단말/VPN/SSO 재시작/외부 heartbeat와 백업 복구. 새 migration, 전송,
권한 부여와 배치는 각각 별도 승인·검증 없이 시작하지 않는다.
