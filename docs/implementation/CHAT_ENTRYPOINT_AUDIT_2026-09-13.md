## 2. 이미 갖춘 기능과 보완할 부분

현재 명령은 `/help`, `/start`, `/status`, `/errors`, `/ack ID`, `/jobs`,
`/worker start|stop`, `/pause`, `/resume`, `/cancel JOB_ID`, `/retry JOB_ID`,
`/features`, `/install ID`, `/guide ID`다. Telegram은 `/cancel`, `/reset`,
`/새대화`를 수신기에서 따로 처리한다. `/tone`과 `/말투`는 같은 말투 메뉴다.

기계식 명령은 Telegram AI 실행 중에도 접수할 수 있다. 단, 같은 전송 경로의 네트워크
지연까지 없어지는 것은 아니다. 일반 요청은 👀 반응 뒤에 AI를 시작하며, 내부 작업
설명과 호스트 결과는 숨기고 최종 답변·질문을 전달한다.

| 우선 보완 | 현재 근거 | 필요한 결과 |
|---|---|---|
| 찾기 쉬운 명령 | `reception/commands.go:12`의 긴 도움말, Telegram 메뉴 등록 코드 없음 | 자주 쓰는 명령을 짧게 노출하고 상세 용법은 해당 명령에서 안내 |
| 읽을 수 있는 상태 | `reception/host.go:101`, `commands.go:102`의 JSON 출력 | 수신 상태, 진행 중 요청, 필요한 조치부터 선택한 언어로 표시 |
| 운영 감시 연결 | 채팅 `/status`는 수신기·컨트롤러를 읽지만 독립 감시기 결론은 안 읽음 | 감시기 미실행·오래된 관측·미해결 경보를 구분해서 표시 |
| 오류별 다음 행동 | `receiver.go:39`의 일반 실패 문구, timeout 분류는 주로 `/errors`에 있음 | 시간 초과·AI 불가·작업 실패·결과 불확실을 구분해서 즉시 안내 |
| 중단의 끝 표시 | `receiver.go:371`은 중단 요청을 답하지만 `:281`의 완료 처리는 상태만 갱신 | 정리 완료와 확인이 필요한 상태를 실제 결과에 따라 안내 |
| 새 대화와 복구 구분 | `receiver.go:373`의 실행 정리가 실패해도 맥락 초기화 후 같은 새 대화 문구를 답함 | 대화 맥락 초기화와 실행 복구 결과를 구분하고 남은 AI 차단 안내 |

추가 경계: 재시작 때 `recoverReceipts`는 중단된 요청을 로컬 오류로 기록하지만
채팅으로 별도 통지하지 않는다. 👀 반응 전달을 확인하지 못한 요청도 기존 정책에 따라
AI를 시작하지 않고 오류를 남긴다. 두 경우 모두 새 메시지 전송 정책을 정해야 하는
부분이며, 이미 선택한 접수 표현의 결함으로 취급하지 않는다.

## 3. 명령 창구 제안

Telegram 기본 메뉴는 기존 명령 중 아래 여덟 개를 우선 노출한다.

| 메뉴 명령 | 설명 |
|---|---|
| `/help` | 할 수 있는 일과 명령 보기 |
| `/status` | 지금 연결·처리 상태 확인 |
| `/jobs` | 맡긴 작업과 결과 상태 확인 |
| `/errors` | 오류와 다음 조치 확인 |
| `/cancel` | 현재 AI 답변 중단 요청 |
| `/reset` | 실행 정리 후 새 대화 |
| `/tone` | 말투 설정 |
| `/features` | 사용 가능한 기능 보기 |

업무 큐·worker 제어, 작업별 취소·재시도, 오류 확인 처리는 `/help`의 운영 항목으로
유지한다. `/cancel`과 `/cancel 작업ID`, `/pause`와 `/worker stop`의 차이를 설명한다.
로컬에서 사용할 수 없는 worker 제어는 로컬 도움말에서 별도로 구분한다.

Telegram의 메뉴용 명령 이름에는 영문 소문자·숫자·밑줄을 사용해야 하므로, 이미
구현된 `/tone`을 메뉴에 등록하고 한국어 설명과 `/말투` 직접 입력을 함께 제공한다.
메뉴 동기화는 `setMyCommands`와 페어링된 개인 대화 범위를 사용하며 기존 목록을
조회·비교한 뒤 변경하는 구성이 적절하다. 실제 BotFather 등록 여부는 이번에
조회하지 않았다. [BotCommand](https://core.telegram.org/bots/api#botcommand),
[명령 등록](https://core.telegram.org/bots/api#setmycommands).

`/status` 출력은 예를 들어 다음처럼 시작한다. 이는 제안 문구다.

> 현재 요청을 받을 수 있어요.
> Telegram 연결은 정상이고, 처리 중인 답변은 없습니다.
> 업무 실행기는 꺼져 있습니다. 작업 목록은 /jobs에서 확인할 수 있어요.
> 운영 감시기는 동작 중이며 현재 경보가 없습니다.

관측이 없거나 오래됐으면 마지막 줄을 ‘감시 상태를 확인하지 못했습니다’로 바꾼다.
프로세스 생존을 모델·도구·다음 응답 성공의 보장으로 표현하지 않는다.

## 4. 오류·중단 안내

기본 흐름은 **👀 접수 → 응답 대기 → 최종 결과 또는 오류·중단 결과**다.
사용자 결정에 따라 지연 안내를 추가하지 않는다. 기존의 30초 후 안내 제안은
철회했다. 내부 작업 설명, 경과 시간 알림, typing 갱신도 이번 범위에 넣지 않는다.

| 상황 | 안내 예시와 조건 |
|---|---|
| 두 번째 일반 요청 | “앞선 요청을 처리 중이에요. 이번 메시지는 대기열에 넣지 않았습니다. 앞선 답변을 기다리거나 /cancel로 중단한 뒤 다시 보내 주세요.” |
| 시간 초과 | “응답 제한 시간에 도달해 이번 답변을 완료하지 못했어요. 이미 시작된 작업은 /jobs에서 확인해 주세요. 오류 ID: …” |
| 처리 실패 | “요청을 완료하지 못했어요. /errors에서 원인과 다음 조치를 확인해 주세요. 오류 ID: …” |
| 결과 불확실 | “이전 요청이 완료됐는지 확인하지 못했어요. 다시 실행하기 전에 /jobs와 /errors를 확인해 주세요.” |
| 중복 중단 요청 | “현재 답변 중단을 이미 요청했습니다.” — 정리 중에 명령을 다시 보냈을 때 |
| 중단 정리 완료 | “현재 답변을 중단했어요. 이미 시작한 작업은 /jobs에서 확인할 수 있어요.” — 정리 성공 후에만 |
| 정리 실패·이전 실행 확인 필요 | “이전 실행을 확인하지 못해 새 AI 요청을 시작할 수 없어요. /status와 /errors는 사용할 수 있어요.” |

활성 답변에 보낸 첫 `/cancel`·`/reset`에는 정리 결과를 확인한 뒤 한 번 답한다.
원 요청의 결과 기록과 중단 명령의 답장 기록은 구분한다.

확인되지 않은 진행률·남은 시간·예상 완료 시각은 만들지 않는다. ‘평소보다 늦다’는
판정도 현재 없는 지연 통계를 근거로 표현하지 않는다. 시간 초과와 취소를 작업의
원상복구로 표현하지 않고, 결과 불확실 상태에서는 무조건 재요청하도록 안내하지 않는다.

## 5. 구현 구조와 전달 경계

| 역할 | 책임 |
|---|---|
| 명령 카탈로그 | 파서·도움말·메뉴가 같은 명령 정의와 용법 사용; 기존 권한 경계 유지 |
| 상태 표시부 | 현재 공개 관측값을 선택한 언어의 짧은 안내로 변환; AI 불필요 |
| 요청 수명주기 | 접수·AI 시작·중단 요청·정리 완료·최종 전송 결과 기록 |
| 안내 정책 | 실제 오류·중단 결과로 문구 결정; 시스템이 문구 소유 |
| Telegram 전송부 | 원 요청 답장과 중단 명령 결과를 구분하고 기존 전송 제한 적용 |
| 독립 운영 감시기 | 주요 흐름과 자기 관측의 신선도를 제공; 대화나 작업을 재실행하지 않음 |

감시 상태의 공통 DTO/읽기 기능은 수신기나 AI를 import하지 않는 작은 계층으로
분리한다. 현재 `opsmonitor → chatsupervisor → telegramchat → reception` 의존성이
있으므로 reception에서 opsmonitor를 직접 import하면 순환한다. 감시 판정 로직을
채팅 쪽에 복사하지 않는다.

현재 `Receiver.send`는 최종 reply 상태·digest·message ID를 갱신한다. 중단 명령에
대한 안내가 원 요청의 최종 전달 기록을 덮어쓰지 않게 구분한다. 정리 완료는
실행 종료를 확인한 뒤 알리며, 이미 완료된 요청을 중단했다고 표현하지 않는다.
안내 전송이 불확실하면 자동 반복하지 않는다.

접수 시각과 최종 전달 시각은 신규 요청부터 실제 이벤트에서 기록한다. 기존 receipt의
수정 시각을 새 접수 시각으로 재해석하지 않는다. 메시지 원문·내부 reasoning·토큰은
새 관측 기록에도 포함하지 않는다. 기계식 안내 문구에 추가 AI 호출을 요구하지 않는다.

재시작 후 중단 통지, 반응 실패 후 별도 안내, 전송 불확실 안내의 재시도는 전달
계약을 별도로 정한다. 안내를 추가해도 원 작업 자동 재실행이나 새 `/restart` 권한은
추가하지 않는다. 채팅 경로 전체가 끊기면 현재 복구 창구는 로컬/SSH이며,
외부 이메일 알림은 [운영 감시 계약](../contracts/operations-monitor-v1.md)의 별도 범위다.
