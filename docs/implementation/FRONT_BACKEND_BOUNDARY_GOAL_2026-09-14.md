# PROC — 외부 수신·대화와 내부 실행의 생명주기 분리

상태: 승인 범위 구현·검증·로컬 반영 완료. 2026-09-14 사용자가 외부 채널 및 공통 대화·명령
처리를 내부 업무 실행과 엄밀히 분리하고, 앞단을 유지한 채 채팅으로 뒷단을 복구하는
작업을 Goal로 등록하고 실행하도록 요청했다.

## 승인 목표

Telegram 등 외부 수신과 공통 대화·고정 명령을 원격 관리의 앞단으로 유지한다.
업무 실행기 미설정·업무 실패·컨트롤러 중지는 이 앞단을 종료시키지 않는다.
기존 OS 서비스·채팅 감독자는 앞단 프로세스를 감독하고, 독립 감시기는 앞단과
뒷단의 상태를 구분해 관측한다. 감시기를 업무별 AI 관리자나 자동 업무 재실행기로
확장하지 않는다.

컨트롤러 복구 명령은 죽은 컨트롤러의 소켓을 유일한 통로로 삼지 않는다. 인증된
채팅의 명시적 고정 명령이 호스트의 기존 사용자 OS 서비스 관리 경로를 이용한다.
임의 shell, 다른 호스트·다른 사용자 프로세스의 제어 권한은 제공하지 않는다.

## 역할과 실행 경계

| 영역 | 역할 | 다른 영역 장애 시 동작 |
|---|---|---|
| 외부 어댑터 | 인증된 수신, 접수·응답 전달, 채널별 연결·receipt | 업무 실행을 소유하지 않음 |
| 공통 대화·명령 | 대화 문맥, 허용된 작업 요청, 고정 관리·복구 명령 | 컨트롤러·업무 AI가 없어도 관리 명령 유지 |
| 컨트롤러 | 한 데이터 홈의 유일한 SQLite writer, 상태·큐·작업 제어 | 업무 실행기 불가 상태에서도 관리 역할 유지 |
| 업무 실행 기능 | 실행 가능 여부를 검사하고 큐의 업무를 기존 executor 자식 프로세스에 배정 | 실패가 수신기 종료로 전파되지 않음 |
| 기존 감독·감시 | 앞단의 생존 복구 및 주요 흐름 사실 관측 | 뒷단 중지를 앞단 장애로 혼동하지 않음 |

새 Slack 어댑터 구현은 범위 밖이다. 이미 구현된 공통 접수 계층을 사용하고,
내부 프로세스 소유권과 복구를 Telegram 전용 처리에서 제거한다. 인증·권한을
검증하지 않은 임의 채널을 허용하지 않는다.

## 관리 명령의 의미

- `controller start`: 업무 AI 없이도 관리 서비스를 시작하고 실제 준비 상태를 확인한다.
- `controller stop/restart`: 알려진 대상만 제어한다. 진행 중 업무·설정 작업이 있으면
  거부하며, 확인되지 않은 상태를 유휴 상태로 단정하지 않는다.
- `worker start`: 컨트롤러 안의 업무 배정을 활성화한다. 필수 실행기 설정 검증에
  실패하면 원인을 반환하고 컨트롤러는 유지한다.
- `worker stop`: 새로운 업무 배정을 중지하며 이미 진행 중인 업무를 임의 취소하지 않는다.
- `worker restart`: 진행 중인 업무가 없을 때 실행 기능을 다시 준비한다.
- 고정 `/controller …`, `/worker …` 명령은 AI가 없어도 처리한다. 일반 대화는
  기존 선언된 capability와 사람의 권한 범위를 유지한다.

여기서 worker는 독립 상주 DB writer를 뜻하지 않는다. 단일 컨트롤러 내부의 업무
배정 기능과 기존 업무 실행 자식 프로세스를 사용한다. 현재 `worker`와 `setup serve`를
옆에 함께 띄우는 방식으로 분리하지 않는다. 기존 독립 실행 서비스는 자동으로
강제 종료·교체하지 않는다.

언어·말투·지연 안내 제외·오류/중단 구분·불확실한 실행과 전달의 재실행 금지 원칙을
유지한다. 컨트롤러 서비스 등록과 업무 실행 의도는 채팅 등록과 분리하며, 기존
worker 의도는 유효성 확인 후 명시적으로 이관한다. 기존 명시적 중지 상태를 오래된
마커로 되살리지 않는다. DB 스키마 변경과 실행 계정·권한 자동 설정은 하지 않는다.

새 테스트 소스는 작성하지 않는다. 기존 영향 패키지 검사·빌드·정적 검사와 분리된
데이터 홈의 CLI·OS 서비스 흐름을 사용한다. 실제 계정의 메시지 발송·장애 주입은
별도 범위로 두며, 검증한 경로와 소스 검토만 한 경로를 구분해 기록한다.

## 시작 관측

직전 점검에서 Telegram의 worker 시작 요청과 실행 의도 저장은 확인됐지만, task
실행기 미설정으로 프로세스가 종료됐다. 기존 관리 컨트롤러가 이미 종료된 뒤여서
컨트롤러 소켓도 사라졌고 독립 감시기는 `controller_unavailable`을 기록했다.
Telegram 수신·감독 프로세스는 계속 실행 중이었다. 이 작업은 이 모드 교체 경로를
상주 컨트롤러와 독립적인 앞단으로 변경한다.

## 완료 관측

2026-09-14 03:12:36 UTC 운영 관측에서 `frontend_health=ready`,
`controller.available=true`, `controller_ready=true`를 확인했다. 기존 task route
미설정은 `worker_not_configured`와 `backend_health=degraded`로만 표시된다.
기존 사용자 실행 의도는 이관했고, 업무 계정·모델·자료 공개 승인은 바꾸지 않았다.
[검증 기록](../validation/FRONT_BACKEND_BOUNDARY_2026-09-14.md)과
[복구 안내](../setup/PROCESS_RECOVERY.md)에 실제 수행 범위와 제한을 기록했다.

## 후속 PROC-06 — 채팅에서 운영 매뉴얼 조회

2026-09-14 사용자가 구조와 사용 스크립트·매뉴얼을 채팅 모듈에서도 확인할 수
있어야 한다고 요청했다. `/guide` 목록과 `/guide runtime` 읽기 전용 안내를
공통 접수 계층에 연결하고, 접수 AI도 동일 번들 문서를 읽어 설명하도록 보완한다.
문서 조회는 실행 명령·설정 설치·계정 권한을 추가하지 않는다.

상태: 구현·검증·앞단 반영 완료. 새 테스트 소스 없이 영향 검사, 컨트롤러와 AI가 없는
분리 홈의 문서 조회, 실제 AI의 문서 조회·설명, 기존 서비스 안내 회귀를 확인했다.
[PROC-06 검증 기록](../validation/CHAT_RUNTIME_MANUAL_2026-09-14.md)에 운영 반영과
그 과정에서 확인한 기존 재시작 경합을 구분해 기록했다.

## 후속 PROC-07 — Telegram 재시작을 하나의 완료 확인 절차로 정리

사용자가 `restart` 한 번으로 종료 후 재시작하도록 요청했다. 같은 데이터 홈의
Telegram 변경 명령을 직렬화하고, 중지 의도를 유지한 채 OS 서비스와 기존
감독자·수신기의 종료 및 소유권 반환을 확인한 다음 새 프로세스를 시작한다.
새 감독자와 그 수신기의 실제 polling 준비 상태까지 확인해야 성공으로 반환한다.
종료 확인 실패 시 시작하지 않으며, 시작 확인 실패 시 성공으로 간주하거나
업무·응답을 자동 재실행하지 않는다. 컨트롤러·워커의 수명주기는 바꾸지 않는다.

상태: 구현·검증·운영 반영 완료. 새 테스트 소스 없이 영향 패키지 검사, 분리 홈의
실패·종료 경로, 유휴 운영 앞단의 실제 재시작을 확인했다. 새 수신기의 connected
확인 후 성공했고 기존 컨트롤러 PID는 유지됐다.
[PROC-07 검증 기록](../validation/TELEGRAM_RESTART_2026-09-14.md)에 범위와 제한을 기록했다.

## 후속 PROC-08 — 자연어 워커 제어의 실패 원인 안내

Telegram 자연어 요청이 `stop_worker` 성공 뒤 `start_worker` 실패로 끝났지만,
공통 접수가 backend의 안전한 원인 안내를 일반 host_failed 문구로 덮어썼다.
업무 실행기 미설정 등 호스트가 작성한 워커 제어 안내만 실패 응답과 추적에
보존한다. 실제 오류·실행 불확실성 구분과 자동 재시도 금지를 유지하며, 임의
오류 원문을 공개하거나 업무 실행기·계정·권한을 자동 선택하지 않는다.

상태: 수정·검증·앞단 반영 완료. 실제 AI의 분리 홈 요청에서 원인 안내와 실패
추적을 확인했다. 워커 실행 설정 자체와 자연어 capability 확장은 범위 밖이다.
[PROC-08 검증 기록](../validation/WORKER_FAILURE_GUIDANCE_2026-09-14.md)에 증거와 제한을 기록했다.

## 후속 PROC-09 — 업무용 AI 설정 저장·복원과 채팅 변경

사용자가 최초 업무용 AI 선택을 저장·복원하고 채팅에서도 수정하도록 승인했다.
기존 config.json의 task executor를 설정의 기준으로 유지한다. `/worker config`로
조회하고, `use reception|use review`로 이미 로컬에 등록된 실행 설정을 복사하거나
`model MODEL`로 업무용 모델을 바꾼다. 복사는 시점의 설정을 저장하며 원본 변경을
자동 추종하지 않는다. 설정을 저장하는 동작과 워커 시작은 별도 명령이다.

변경은 단일 writer인 컨트롤러의 IPC로 처리하며 워커 중지와 업무·설정 작업의
유휴 상태를 요구한다. 컨트롤러가 없으면 먼저 시작하도록 안내한다. 경로·토큰·
새 실행 계정·자료 접근 승인은 채팅 입력으로 받지 않는다. 변경한 task의 자료
공개 승인은 기존 CLI와 같이 해제하며, 기존 reception/review의 유효 설정은 보존한다.
설정 조회와 재시작이 최초 설정을 임의 생성하거나 명시적 중지를 되돌리지 않는다.

자연어 설정 조회·변경 capability와 단일 restart_worker를 같은 호스트 경로에
연결한다. 실제 결과가 확인돼야 저장·시작 성공을 안내한다. 저장/IPC 결과가 불명확하면
자동 재시도하지 않고 설정과 상태 조회를 안내한다.

상태: 구현·검증·운영 반영 완료. 새 테스트 소스 없이 분리 홈의 저장·변경·복원,
권한 및 상속 보존, 중지/진행 중 경계, 실제 AI 설정·단일 재시작 요청과 영향 패키지
검사를 확인했다. 운영 최초 task 선택은 자동으로 하지 않았으며 현재 접수 실행기의
업무용 버전 검증 차이는 별도 조건이다.
[PROC-09 검증 기록](../validation/WORKER_CONFIGURATION_2026-09-14.md)에 증거와 제한을 기록했다.
