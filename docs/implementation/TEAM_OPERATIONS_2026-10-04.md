# TEAM — 팀 업무 누락 방지와 저소음 온콜

[상위 계획](../../IMPLEMENTATION_PLAN.md)

작성일: 2026-10-04 (Asia/Seoul)

상태: TEAM-00 설계·준비 완료. 아래 상태·권한·배치 구조는 구현 전 검토안이며,
TEAM-01 이후 기능의 구현·실운영·스키마 변경을 완료했다는 뜻이 아니다.
이번 작업은 제품 코드, 운영 데이터, 실행 중 서비스, 계정 연결을 변경하지 않는다.

## 1. 목표와 결정된 원칙

춘수는 대화량을 늘리는 챗봇이 아니라, 팀 업무의 약속과 실제 진행을 비교하고
누락·위험을 판단해 적절한 사람에게 알리며 후속 조치를 추적하는 시스템이다.
챗은 설정 초안 작성, 조회, 확인, 승인, 피드백의 인터페이스다.

사용자가 선택한 요구사항:

1. 일정 준수뿐 아니라 배포 주기별 약속한 작업의 완료·배포 여부와 미완료 이유를 확인한다.
2. 반복 수집되는 Slack 대화에서 긴급 사안을 판단하고 강도별 메신저 온콜을 제공한다.
   중복·불필요한 호출을 줄이되 중요한 누락을 숨기지 않는다.
3. 준비·진행중·대기·완료 등 업무 상태는 춘수가 소유한다. Jira 상태는 참고 근거이며
   외부 변경이 내부 상태를 무조건 덮어쓰지 않는다. 일정 초과·변경은 별도로 관리한다.
4. AI는 읽기·맥락 연결·판단·설명에 사용한다. 권한·시간 계산·영속화·전달은 코드가 강제한다.
5. 사내 Jira/메일 접근이 가능한 상시 가동 단말을 전제로 팀 사용을 준비한다.
6. 실제 수행 결과와 피드백으로 내부 스킬 후보를 만들고 검증·승인·되돌리기로 개선한다.

이번에 제외하는 것: 범용 시각적 DAG 편집기, 임의 코드 실행 스킬, 자동 Jira 변경,
메일 발송, 자동 배포, 무승인 스킬 채택, 무제한 자율 에이전트, 즉시 EC2/사내 배포.
메신저 온콜은 호출·확인·상향 전달이며 전화/SMS 서비스까지 선정한 것은 아니다.

## 3. 배치 제안: 사내 단말이 실행과 데이터의 중심

첫 배치는 사내 네트워크/VPN에서 승인된 Jira·메일을 읽을 수 있는 관리형 상시 단말 한 대다.
수집기, controller/SQLite, 판단 작업, 알림 발송기를 그 단말에서 운영한다.
EC2와 실행 상태를 이중 관리하거나 원문을 외부 서버로 복제하는 것은 초기 범위에서 제외한다.

- 회사가 허용한 전용 실행 계정과 자격증명 저장소를 사용한다. 개인 브라우저 로그인이나
  개인 계정 세션을 복사해 접근 제한을 우회하지 않는다.
- Slack 내부 앱의 Socket Mode는 공개 수신 URL 없이 이벤트를 받는 후보다.
  단말의 외부 WebSocket/HTTPS 연결, 앱 설치·채널 읽기·메시지 권한은 별도 승인·검증한다.
- 사내 접근 가능과 외부 AI에 내용을 전송할 권한은 다르다. 승인된 실행 환경·모델과
  소스별 공개 범위, 보존·마스킹 정책을 확정하기 전에는 실데이터를 모델로 보내지 않는다.
- 외부 메신저에는 수신자 권한에 맞춘 최소 요약만 전달한다. 원문 링크도 접근 권한을
  부여하지 않으며 제목·요약 자체의 정보 유출을 확인한다.
- 절전·재부팅·VPN 만료·SSO 만료·네트워크 단절을 관측한다. 수집 끊김은 정상 상태가
  아니라 `unknown/stale`이다. 복구 후 누락 구간을 보충하고 수집 커서를 복원한다.
- 단말 자체 장애는 내부 프로세스만으로 감지할 수 없다. 외부 heartbeat 감시를 별도
  선택하고, 외부 전송이 불허되면 그 감지 불가능 범위를 명시한다.
- 운영 DB와 백업은 승인된 로컬 저장소에 두고 보호·보존·복구 정책을 정한다.
  업데이트의 migration 거부를 유지하며 스키마 변경은 백업·전환·복구 절차로 분리한다.

공식 근거: [Slack Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/),
[Events API](https://docs.slack.dev/apis/events-api/),
[API 제한](https://docs.slack.dev/apis/web-api/rate-limits/) (2026-10-04 확인).
연결 방식의 지원은 해당 회사 단말의 네트워크·보안 승인을 입증하지 않는다.

## 4. 핵심 데이터 의미 — SQL 확정 전 검토안

### 4.1 세 가지 상태를 분리한다

| 상태 축 | 예시 | 소유자/의미 |
|---|---|---|
| 업무 상태 | 준비, 진행중, 대기, 완료, 취소 | 팀의 실제 업무 생애주기 |
| 실행 상태 | 대기열, 실행중, 입력대기, 실패, 완료 | 기존 FLOW job/step; 보고 작업 완료 ≠ 업무 완료 |
| 위험·변경 표식 | 일정 초과, 배포 누락, 일정 변경, 근거 부족, 외부 상태 불일치 | 계산/판단 결과; 여러 표식 동시 존재 가능 |

업무에는 내부 ID, team/project, 담당자, 완료 기준, 상태 변경 이력, 연결 소스 ID가 있다.
대기는 사유·해소 책임자·다음 확인 시점을 가진다. 대기로 바꿔도 기한이 자동 연장되지 않는다.
완료는 검증 가능한 완료 근거와 승인된 전이 정책을 요구한다. 재개·취소도 이유를 남긴다.

Jira 상태, Slack 발언, 메일은 시간·출처·범위와 함께 관측 사실로 저장한다.
외부 상태 매핑은 내부 전이의 제안만 생성한다. 초기에는 담당자/관리자가 내부 전이를
확인하며, 자동 전이는 특정 근거·전이만 사람이 정책으로 승인한 뒤 허용한다.
늦게 도착한 이벤트는 과거 관측으로 남기고 현재 상태를 되돌리지 않는다.
동시 수정은 revision으로 충돌을 드러내며, 사람의 확정을 모델 판단이 덮어쓰지 않는다.
AI의 업무 연결이 애매하면 후보로 남기며, 서로 다른 업무를 자동 병합하지 않는다.

### 4.2 일정과 배포 약속

업무 일정에는 최초 기준일, 현재 승인된 기준일, 변경 제안·사유·행위자·승인 시각을 구분한다.
현재 기한 대비 초과와 최초 약속 대비 이동을 각각 표시한다. 날짜를 미뤄도 과거 지연과
변경 이력이 사라지지 않는다. 날짜·시간대·업무일·유예 기준은 팀 설정이다.

배포 주기에는 ID, 대상 서비스/환경, 마감·예정 배포 시각, 확정 대상 목록의 버전,
필수 준비 조건, 실제 배포 근거를 둔다. 스프린트와 배포 주기를 자동으로 동일시하지 않는다.
대상 추가·제외·다음 주기 이월은 승인과 사유를 보존한다.

반드시 구분할 판정:

- 이번 배포 대상으로 약속했으나 준비/업무가 완료되지 않음.
- 작업은 완료됐으나 해당 환경 배포 근거가 없거나 아직 배포되지 않음.
- 실제 배포 근거는 있으나 내부/Jira 완료 처리가 남아 있음.
- 승인된 제외/이월/취소로 이번 배포 대상에서 빠짐.
- 소스가 불완전하여 배포 여부를 판단할 수 없음.

미배포 사실과 미배포 근거 부족을 혼동하지 않는다. 배포 증거는 승인된 CI/CD 기록,
릴리스 기록 또는 지정 책임자 확인 등에서 선택하며, 연결 전에는 사람 확인을 사용한다.
AI는 원인·차단 요인·다음 조치와 근거를 설명하되, 추측을 확정 사유로 저장하지 않는다.

### 4.3 별도 기록

`WorkItem`, `ScheduleRevision`, `ReleaseCycle/Commitment`, `SourceObservation`,
`Assessment`, `Incident`, `NotificationAttempt/Acknowledgment`, `SkillCandidate`
는 논리적 개념이다. 실제 필드·테이블·마이그레이션 계약은 TEAM-01에서 검토한다.
관측, 판단, 업무 전이, 알림 전송, 사람 확인은 각각 별도 사실로 보존한다.

## 5. Slack 수집과 판단

허용한 채널·프로젝트부터 수집하며 DM/비공개 채널은 별도 범위 결정 없이는 제외한다.
기존 로그 수집기가 있다면 저장 입력 어댑터를 먼저 붙일 수 있다. 실제 API 이벤트 수신과
저장 로그 가져오기는 동일한 관측 형식으로 변환하되 출처·수집 보장 수준을 보존한다.

처리 단계: 영속 수신 → 중복/변경 판별 → 허용 범위 내 스레드·관련 업무 보충 →
AI 판단 → 정책/근거 검증 → incident 갱신 → 알림 대기열 → 전달/확인 추적.

- 이벤트 ID·메시지 ID·버전으로 중복 수신, 수정·삭제, 지연·역순 도착을 처리한다.
  수신 확인과 업무 처리 완료를 분리하고, 저장되지 않은 입력을 처리 완료로 표시하지 않는다.
- 재연결 보충 조회는 rate limit과 Retry-After를 존중한다. 권한·보존기간 등으로 복구
  불가능한 구간은 누락으로 남긴다. 삭제 자료는 회사 보존 정책에 따라 원문/파생물까지 처리한다.
- 단순 키워드만으로 메시지를 버리지 않는다. 변경·중복·범위 필터로 비용을 줄이고
  제한된 맥락을 AI가 읽어 영향, 시급성, 진행 중 대응, 담당자, 모호함을 판단한다.
- 결과에는 관측 시각, 영향 서비스/사용자, 권장 심각도, 근거 링크/구간,
  불확실성, 관련 업무/incident 후보, 권장 조치를 요구한다.
- 소스 안의 명령은 자료이지 권한이 아니다. 메시지로 호출 대상·권한·활성 스킬을 바꾸지 못한다.
- AI 오류·예산 소진·대기열 지연은 분석 불능으로 관측한다. 사전 승인된 명시적 호출
  신호는 AI 없이도 지정 수신자로 전달할 수 있게 설계하되, 키워드로 임의 긴급 호출하지 않는다.
- 초기 단일 AI 실행 슬롯에서 긴급 판단이 긴 보고 작업에 묶일 수 있다. 판단 대기시간을
  측정하고 짧은 단계·우선순위 admission을 검토한다. 동시 executor 증설은 별도 결정이다.

## 6. 온콜과 노이즈 정책

다음은 명칭과 의미의 초안이다. 팀별 영향 기준·응답 시간·반복 간격·업무시간·대체 담당자를

|---|---|---|
| P0 긴급 | 현재 중대한 영향, 즉시 대응 필요 | 승인된 당번/대체자 즉시 호출; 미확인 시 정책상 상향 전달 |
| P1 높음 | 빠른 대응이 필요한 위험/배포 차단 | 담당자 즉시 알림; 응답 기한 이후 상향 전달 |
| P2 경고 | 계획된 확인·조치가 필요한 지연/누락 | 업무시간 알림 또는 묶음 요약 |
| P3 정보 | 상태 변화·참고 사항 | 현황/정기 요약 중심, 기본 개별 호출 없음 |

심각도와 확신도는 별개다. 영향이 크지만 근거가 불확실하면 '확인 필요'임을 알린다.
확신이 낮다고 무조건 낮은 등급으로 숨기거나 확정 장애로 표현하지 않는다.

노이즈 제어:

- incident 단위로 여러 메시지와 소스를 묶고 새 근거·영향 확대·상태 변화 때만 갱신한다.
  병합 확신이 없으면 검토 대상으로 두고 다른 장애를 숨기지 않는다.
- cooldown·묶음 발송·시간 제한 snooze는 범위와 만료를 갖는다.
  승인된 P0 정책의 우회 조건을 명확히 하고, 심각도 상승은 기존 억제에 갇히지 않게 한다.
- `전달됨`, `확인함`, `대응중`, `해결됨`을 구분한다. 확인이 해결은 아니다.
  해결 후 새 증거가 나오면 재개 이력을 보존한다.
- 당번표·부재·대체자·시간대를 관리한다. 수신자 미설정은 실패이며 '알림 완료'가 아니다.
- 알림 대기열은 영속화하고 수신자·incident·알림 revision별 중복을 막는다.
  전송 결과가 불명확하면 unconfirmed로 남기며 provider의 멱등성/조회 기능이 없는 한
  무작정 재전송해 정확히 한 번 전달됐다고 주장하지 않는다.
- 저소음은 누락률과 함께 평가한다. '알림이 줄었다'만으로 개선을 주장하지 않는다.

초기 실데이터 검증은 shadow 모드(판단 기록, 실제 호출 없음)로 수행한다.
팀이 사례·수신자·정책을 확인한 뒤 제한된 호출을 켠다. 정식 가동 후 매 알림을 사람이
미리 승인해야 하는 구조는 피하고, 승인된 정책 범위 안에서 자동 전달한다.

## 7. 팀 사용과 내부 스킬 성장

### 팀 사용

최소 역할은 관리자(정책/연결/스킬 승인), 담당자(배정 업무 확인·상태/조치),
조회자(허용 프로젝트 열람)로 제안한다. 실제 권한표와 사용자 식별은 구현 전에 확정한다.
외부 사용자 ID를 검증된 팀 사용자에 연결하고 메시지 본문의 이름은 인증으로 쓰지 않는다.
각 조회·전이·승인·알림 상세에 team/project 권한을 검사한다. 알림 링크 재조회도 재검사한다.
권한 철회 시 대기 중 전달/실행을 재검사하고, 팀 간 원문·피드백·스킬 사례가 섞이지 않게 한다.

최소 운영 화면/명령: 업무·배포 현황, 위험 항목, 미확인 호출, 조치/승인함,
수집 최신성·누락 구간, 실행 근거, 스킬 버전·비교·되돌리기.
초기 shadow 검증은 기존 단일 운영자 경로로 가능하지만, 실제 팀 접근과 다중 수신자
호출은 사용자 식별·권한·수신 범위를 구현하고 검증한 다음 연다.

### 내부 스킬

여기서 스킬은 춘수 제품 내부의 버전 관리 업무 지침이며 Codex 개인 스킬 설치가 아니다.
기존 workgroup Skill/후보/비교/채택 경로를 확장한다. 현재 정해진 workgroup 목록 밖의
스킬 실행이나 팀 단위 scope는 이미 지원된다고 가정하지 않는다.

후속 승인된 [TEAM-08A 공통·팀·프로젝트 관리](SCOPED_SKILLS_2026-10-04.md)는 현재
owner-operated namespace와 정확한 버전 조합을 구현한다. 공통 판단 방법, 팀 관행,
프로젝트 지침을 중앙 저장하되 실행/채택 대상 scope가 명시한 digest 목록만 사용한다.
상위 변경은 다른 범위에 자동 전파하지 않는다. 작업 기록·현재 프로젝트 사실·재사용
Skill은 구분하고 피드백 출처는 실행 지침과 따로 보존한다. 이 scope는 다중 사용자
인증·팀 데이터 격리를 제공하지 않는다. 팀 사용 권한은 TEAM-05의 별도 구현이다.

수행 결과에는 사용한 스킬·정책 버전, 입력 근거, 판단·알림·사람 조치 이력을 연결한다.
피드백은 '오탐/누락/등급 오류/담당자 오류/중복/근거 부족/유용함'과 교정 근거를 기록한다.
단일 사용자의 무응답을 정답으로 보거나, 메시지 반응만으로 활성 기준을 변경하지 않는다.

성장 흐름:

1. 수행 결과와 피드백을 재사용 가능한 사례 후보로 정리한다.
2. 민감정보를 제거·최소화하고 원본 접근 권한과 사례 사용 범위를 확인한다.
3. AI가 좁은 개선 가설과 스킬 변경 diff를 제안한다. 새 코드는 실행하지 않는다.
4. 동일 입력의 기존/후보 결과와 별도 확인 사례를 비교한다. 오탐뿐 아니라 중요한 누락,
   알림 부담, 근거 정확도, 비용도 확인한다. 독립 사례가 없으면 한계를 표시한다.
5. 지정된 사람이 공통·팀·프로젝트별 정확한 버전 조합을 채택·거절한다. 즉시 rollback 경로를 제공한다.

스킬에는 목적, 적용 범위, 읽기/판단 기준, 완료 근거, 출력 형식, 애매한 사례,
개선 근거·버전 정보를 관리한다. 비밀값·개인정보 원문·숨겨진 추론 과정은 저장하지 않는다.
권한·알림 목적지·비용 한도는 host 정책이며 스킬 문서로 확대할 수 없다.
실행은 시작할 때 버전을 고정하며 스킬 채택이 진행 중 판단을 몰래 변경하지 않는다.

팀이 정하며 합성 시나리오 통과만으로 운영 신뢰성·유용성을 주장하지 않는다.

## 10. 이번 작업의 검증 경계

실행한 확인: 현재 checkout 상태, 기존 계획·관련 코드·검증 기록 확인,
Slack 공식 연결/제한 문서 확인, 변경 문서의 상대 링크 존재·공백 오류·diff 검토.
코드 변경이 없어 Go 테스트·빌드·서비스 실행은 하지 않는다.
실데이터 수집, 새 권한 부여, 스키마 migration, 외부 발송, 단말 배포, push는 하지 않는다.
