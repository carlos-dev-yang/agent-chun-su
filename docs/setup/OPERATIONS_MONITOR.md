# 운영 감시 실행하기

운영 감시기는 AI 없이 주요 흐름의 생존·준비·처리 결과를 확인한다. 채팅 수신기나
업무 컨트롤러와 별도 프로세스로 실행되며 같은 SQLite 파일을 작성하지 않는다.
[운영 계약](../contracts/operations-monitor-v1.md)에 관측·알림 범위가 정의되어 있다.

## 먼저 현재 상태 확인

기존 데이터 홈에서 실행한다. 별도 홈을 사용하는 경우 모든 명령에 같은 `--home`
인자를 사용한다. 이 문서의 명령은 배포 패키지의 `chunsu` 실행 파일을 기준으로 한다.

```sh
chunsu monitor check
chunsu monitor status
```

`check`는 현재 소스에서 읽은 관측값을 출력한다. `status`는 감시 프로세스와 보존된
관측·경보 상태를 확인한다. 감시가 실행되지 않았거나 기록이 오래되었다면 저장된
결과만 보고 현재 정상이라고 판단하지 않는다.

프로세스 생존, Telegram 수신, AI 처리 가능 여부, 컨트롤러 응답과 요청 결과는
각각 다른 사실이다. 오래된 마지막 답변 시각만으로 조용한 채팅을 장애로 보지 않는다.
과거 기록에 없는 단계별 시각은 미관측 상태로 남는다. 시각이 없는 기존 기록은
현재 JSON에서 0 시각으로 표시될 수 있다. receipt 집계는 디렉터리의 제한된 표본이며
최신순 전체 이력 집계가 아니다. 현재 처리 중인 요청은 ID로 별도 조회한다.
`fixed_reply_observed_at`은 기존 고정 응답 경로의 관측값이다. 일반 AI 응답의
정확한 전송 시각은 이 값으로 추정하지 않는다.

## 감시를 별도 프로세스로 실행

```sh
chunsu monitor run
```

현재 터미널에서 주기적으로 관측하고 로컬 경보를 보존한다. 종료하려면 Ctrl-C를
사용한다. 다른 감시기가 같은 홈을 소유하고 있으면 중복 실행을 거부한다.
감시용 잠금은 업무 컨트롤러 잠금과 별개다.

한 번만 기록하려면 `chunsu monitor run --once`를 사용한다. 종료된 프로세스의
저장값은 `saved: true`여도 `process_alive: false`, `fresh: false`로 표시된다.
주기와 예산은 시작 시 설정에서 읽는다. 관련 설정을 바꾼 뒤에는
`chunsu monitor restart`로 감시기를 다시 실행한다.

OS 사용자 서비스로 실행하려면 먼저 등록 내용을 확인한다.

```sh
chunsu monitor render
chunsu monitor enable
chunsu monitor status
```

macOS는 LaunchAgent, Linux는 systemd 사용자 서비스를 사용한다. 실행 파일과
데이터 홈이 등록에 고정되므로 운영할 바이너리 위치에서 명령을 실행한다.
개발 checkout의 바이너리를 사용하면 그 경로를 유지해야 한다.
Linux에서 로그아웃 후에도 실행하려면 [서버 운영 조건](SERVER.md)을 별도로 확인한다.

```sh
chunsu monitor stop
chunsu monitor start
chunsu monitor remove
```

명시적 중지는 감시기의 실행 의도에 보존된다. 시작·중지·제거는 감시기만 대상으로
하며 기존 Telegram 수신기와 업무 큐는 그대로 둔다. 제거 후에도 관측·경보 기록은
보존한다. 등록된 경로나 로그인 정책을 바꾸려면 현재 등록을 확인한 뒤 제거·재등록한다.

## 경보를 확인하고 직접 복구

현재 알림 대상은 로컬 경보 기록이다. 외부 이메일·macOS 팝업·Telegram 메시지를
발송한 상태로 해석하지 않는다. 같은 문제가 계속 관측될 때 매 주기 새 알림을
만들지 않고 장애 상태를 집계한다. 정상으로 돌아온 상태도 구분해 보존한다.

현재 감지한 문제는 `latest.diagnostics`, 아직 정상화가 확인되지 않은 기존 장애는
`active_diagnostics`, 발생·해제 이력은 `alerts`에서 확인한다. 채팅 서비스가
명시적으로 중지되어 있으면 새 채팅 장애를 판정하지 않는다. 이전 장애는 정상 관측이
확인될 때까지 남으며 중지를 복구 완료로 기록하지 않는다. 읽기 실패도 별도 코드로
남기므로 한 파일의 오류가 다른 구성요소의 경보를 가리지 않는다.

정상 재시도 대기는 `poll.waiting`으로 표시한다. 연결된 poll의 진행 정체와 현재
요청의 예산 초과는 각각 판단한다. 감시기는 과거 receipt의 실패 개수를 현재 진행 중인
장애로 자동 전환하지 않는다. 과거 실패의 상세 확인에는 기존 오류 기록을 사용한다.

문제가 표시되면 다음으로 기존 실행 상태와 오류를 확인한다.

```sh
chunsu telegram status
chunsu errors
```

설정·권한·네트워크 문제를 확인한 뒤 수신기 재시작이 필요하면
`chunsu telegram restart`를 실행한다. 감시기는 이 명령을 대신 실행하거나
중단된 업무를 다시 접수하지 않는다. AI만 사용 불가한 경우에는 Telegram 고정
관리 명령이 계속 동작할 수 있다.

외부 알림 수신처와 발신 권한은 별도로 설정해야 한다. 호스트 전원이나 전체
네트워크 장애를 외부에 알려야 한다면 다른 호스트의 감시가 필요하다.
