# PROC-07 — Telegram 종료 완료 후 재시작

상태: 분리 환경 검증·최종 수정·운영 반영 완료.

## 구현 범위

- 동일 데이터 홈의 enable/start/stop/restart/disable/remove를 별도 수명주기
  잠금으로 직렬화한다. status와 render는 이 잠금을 사용하지 않는다.
- 등록 파일·설치 정의 digest와 기존 프로세스 신원을 먼저 검증한다. 사전 검증
  거부는 실행 의도를 바꾸지 않는다.
- 중지 의도를 저장한 다음 OS 서비스 종료, 이전 감독자·수신기 신원 소멸,
  두 소유권 잠금 반환을 확인한다. 이 단계 실패 시 새 프로세스를 시작하지 않는다.
- 시작 의도 저장 및 OS 시작 후, 새 감독자 자식과 수신기의 신원 일치,
  생존 상태, 새 시작 시각, connected polling, AI 차단 없음까지 확인한다.
- 오류 응답은 시작·종료 의도 저장 실패와 실제 준비·종료 확인 실패를 구분한다.
  컨트롤러·워커 변경이나 업무·답변 재실행을 추가하지 않는다.

## 실제 수행한 분리 환경 검사

봇 binding과 자격정보가 없는 비공개 데이터 홈에 실행 파일이 렌더링한 정의를
그대로 등록하고 macOS 사용자 서비스 명령을 실행했다.

- 준비 대기 중 status는 약 0.02초에 응답했다. 경쟁 stop은 5초 뒤 변경 중 오류로
  거부되어 실행 의도를 바꾸지 않았다.
- 준비 대기를 SIGINT로 취소하면 종료 코드 1, 성공 출력 없음, enabled 의도 유지로
  끝났다. 뒤이은 stop은 종료 확인 후 성공했다.
- 전체 준비 대기는 기본 설정에서 계산된 약 140초 뒤 종료 코드 1로 끝났다.
  연결되지 않은 수신기를 ready로 보고하지 않았고 enabled 의도는 남았다.
- 별도 홈에서 수신기 소유권 잠금을 유지하면 restart가 기다렸고 시작 의도가
  켜지지 않았다. SIGINT 이후 stop 미확인 오류와 disabled 의도를 확인했다.
- 위 서비스는 stop과 remove로 정리했다. 실제 Telegram 계정·토큰·메시지는
  사용하지 않았다. 새 테스트 소스는 작성하지 않았다.

## 검사 범위와 제한

영향 패키지 `cli`, `chatsupervisor`, `platform`, `telegram`, `service`,
`conversation`의 go test와 go vet를 수행했다. 해당 패키지에는 테스트 파일이
없으므로 go test 결과는 컴파일 검사다. macOS 빌드와 Linux amd64 교차 빌드가
통과했다. Linux 사용자 서비스 실동작과 실제 Telegram 메시지 송수신 검증은
수행하지 않았다. 독립 Terra 리뷰에서 최초 연결의 잠금 누락을 찾아 수정했다.
최초 enable의 자동 초기화도 유지했다. 빈 홈에서 enable을 실행하면 config가
생성되고, 검증용으로 지정한 존재하지 않는 토큰 파일에서 연결 전 정상 거부됐다.
최종 수정본의 위 검사와 두 플랫폼 빌드를 다시 통과했고 리뷰의 남은 차단 사항은 없다.

## 운영 반영

수신기가 유휴이며 connected인 것을 확인한 뒤 검증한 바이너리를 반영하고,
`telegram restart`를 한 번 실행했다. 약 30.49초 후 종료 코드 0 및 `ready: true`를
반환했다. 기존 감독자 32703과 수신기 32712는 종료됐고 새 감독자 52033과 수신기
52035가 생존하며 신원이 일치하고 polling이 connected인 것을 확인했다.
컨트롤러 PID 9196은 유지됐다. 컨트롤러·워커 설정은 변경하지 않았으며 기존
`worker_not_configured` 상태도 그대로다. 이후 상태 조회에서도 수신·감독 상태와
enabled 의도가 유지됐다. 실제 사용자 메시지를 보내는 검사는 수행하지 않았다.
