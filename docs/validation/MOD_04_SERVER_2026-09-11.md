# MOD-04 — Portable installation and Linux operation

Technical scope complete. Source: local candidate on top of `95abbe9`;
the final integration package is produced in MOD-07. No public release, EC2
instance or company-account connection was created.

## Changes

- Optional credential-helper protocol behind the existing secret-store interface.
  An approved company helper can replace the macOS Keychain. The separately
  installed sample helper encrypts entries with AES-256-GCM and an independently
  provisioned private key. Secret values travel on stdin, never in arguments.
- Linux terminal secret entry and systemd user-service support. Definitions bind
  absolute executable/data paths and selected host environment paths; startup
  after login is an explicit option. Service commands verify the saved definition.
- OS/CPU archives with embedded SQLite, public assets, dependency versions and
  licenses, source/build manifests and SHA-256 checksums. The installer checks
  target/checksums, preserves application data and does not start services.
- [Server installation and recovery instructions](../setup/SERVER.md) and
  [credential protocol](../contracts/credential-helper-v1.md).

## Checks actually performed

Existing focused runner tests passed; affected Gmail/Jira/secret/service/CLI
packages built and their static checks passed. No new test code was created.
Linux arm64/amd64 and macOS arm64 archives were built. The Linux arm64 archive
was transferred into a separate local Colima Ubuntu VM and installed from its

Actual environment: Ubuntu 24.04, aarch64, kernel 6.8.0-100-generic,
systemd 255.4, SQLite 3.53.4, Codex CLI 0.153.4. The CLI distribution was obtained
from its official npm platform package and its published archive digest checked.
No host AI account credentials were copied into the VM.

Observed outcomes:

1. Setup created schema 4; role-route configuration and doctor worked.
2. A random non-production credential was set, read back and deleted through
   the actual helper process. Ciphertext did not contain the value. A broadly
   readable key and altered ciphertext were rejected. Missing data was explicit.
3. A package upgrade at the same prefix preserved the configured data home.
4. A generated systemd unit passed the installed systemd parser, started a real
   controller, answered management status through its private local socket,
   stopped and reported inactive. The core's single immediate idle measurement
   was 16,524 KiB RSS; this excludes the AI driver and is not a load benchmark.
5. Opt-in startup created the exact user-service link. Removal removed the link
   and registration while preserving data. No service remains active for this
   validation home.
6. A synthetic queued job reached `waiting_auth` with a saved attempt when the
   VM had no AI login. It did not claim a generated report or consume a source
   cursor. Consistent backup verification and restoration into a fresh home
   succeeded; restored connections and route disclosure require review again.
7. The pinned CLI's native Linux sandbox read the permitted package, could not
   read a sibling private file or credential key, refused writes to the mounted
   package, and could not connect a tool socket to the network. A write into an
   unmounted pathname succeeded only in its private filesystem view: checking
   the actual host file afterward proved its contents were unchanged. This is
   host isolation, not a promise that every write syscall returns an error.

## Prerequisites discovered and corrections

The first unit renderer quoted `WorkingDirectory` incorrectly. The systemd
parser rejected it before service startup. The directive was removed because
all managed paths are absolute; the corrected unit was then verified and run.

The minimal VM lacked the user D-Bus service. Installing `dbus-user-session`
and restarting that VM's user manager made the user-service commands work.
The application does not install this OS prerequisite or enable lingering.

Ubuntu's enabled AppArmor user-namespace policy initially prevented the driver's
bubblewrap initialization (`net_admin` denied). A temporary, executable-specific
profile in the validation VM allowed user namespaces for the exact installed
Codex binary. Global AppArmor/sysctl restrictions remained enabled. This follows
[Ubuntu's per-application model](https://documentation.ubuntu.com/security/security-features/privilege-restriction/apparmor/).
The restricted child also needs to read the driver runtime: the validated
distribution was root-owned under `/usr/local/lib`, not under a hidden home
directory. These prerequisites are now explicit in the server instructions.
