# IN-01 / IN-02 — 설정 대화와 호스트 실행 검증

날짜: 2026-09-11. 기준: `d309a3d` 이후 구현, macOS/arm64.
사용자가 앞선 실패 점검 후 설정 전용 대화와 처리 프로세스 구현·구동을 승인했다.

## 구현한 결과

- `chat [REQUEST]`: 서비스 이름·한국어 별칭과 고정 질문으로 설정을 진행한다.
  신규 로컬 환경을 초기화하고, 같은 바이너리의 별도 설정 호스트를 자동 실행한다.
  기존 worker가 있으면 관리 채널로 요청하며 대화 종료가 worker를 종료하지 않는다.
- `setup serve`: AI 작업·스케줄 없이 설정 요청을 처리하는 호스트. worker도 같은
  제한된 설정 요청을 처리한다. Gmail 인증/확인은 비동기 작업으로 진행한다.
- 6개 서비스 설정 팩을 바이너리에 포함하고 해시별 경로에 설치한다. 기존 파일의
  내용이 다르면 덮어쓰지 않는다. 보고용 Skill 패키지는 변경하지 않았다.
- Gmail: 기존 연결 선택과 실제 계정 확인, 새 계정/client 파일/조회 조건 질문,
  브라우저 OAuth 인계, 취소, 결과 표시. OAuth/Keychain 구현은 기존 코드를 재사용한다.
- 설정 ID별 상태 저장과 `setup status`/`setup cancel`. 비밀·인증 URL·입력 대화는
  상태 파일에 넣지 않는다. 호스트가 사라진 미완료 작업은 중단으로 표시한다.

현재 대화는 **LLM을 호출하지 않는 문답형 설정 UI**다. 다른 5개 서비스에는
로컬 자료 설치와 안내만 제공하며 실제 제공자 설치/인증/adapter 완료로 표시하지 않는다.

## 실제 대화·프로세스 확인

| 시나리오 | 관찰 |
|---|---|
| 처음 실행한 새 데이터 경로에서 `chat '구글 드라이브 설치해줘'` | 로컬 setup, DB, 설정 child 시작 후 Drive 안내 질문으로 진입 |
| 같은 대화에서 Figma → GitHub → Slack → Telegram → Gmail 선택 | 각 서비스 매뉴얼 경로와 지원 상태 출력, Gmail은 계정 질문으로 이어짐 |
| Gmail에 잘못된 주소 / 없는 파일 경로 / 도움말 입력 | 대화가 계속되고 수정 입력 또는 Google client 준비 안내 제공 |
| 로컬 `{}` 파일을 client로 선택하고 조회 조건과 ‘시작’ 입력 | 실제 호스트 작업 ID 발급, async 실행 후 Desktop client 오류 표시. OAuth/Keychain 전 단계에서 실패 |
| 질문 중 취소 후 종료 | 서비스 메뉴 복귀, 자동 시작한 child 종료 |
| 실행 중 worker에 별도 chat 연결 후 같은 신규 연결 실패 경로 진행 | writer 잠금 오류 없이 호스트가 처리. `status` 응답 가능. chat 종료 후 worker는 계속 실행 |
| 기존 사용자 Gmail 연결을 chat에서 선택 | **실제 refresh/profile 확인 성공**, 저장된 읽기 범위의 기존 연결 사용 가능 확인. 메일 본문 수집 없음 |
| 호스트 종료 후 `setup status`로 완료/실패 ID 조회 | persisted `connected` / `failed` 확인. 진단 출력에 OAuth URL 없음 |

최초 새 환경 점검에서 내부 setup 호출에 context 전달이 누락되어 panic이 발생했다.
context 전달을 고친 뒤 다른 새 경로에서 초기화·대화·종료를 다시 실행해 성공했다.
이 실패를 포함해 새 환경 경로를 실제 실행했고 소스 확인만으로 통과 처리하지 않았다.

실제 기존 연결 확인은 재로그인 없이 실행했다. 신규 OAuth 승인에 필요한 사용자
입력이 아직 없어 **이번 새 대화 경로로 새 계정을 브라우저 승인한 검증은 하지 않았다**.
기존 Gmail 연결의 성공과 신규 설치 E2E 성공을 구별한다.

## 동시 처리·파일·거부 검사

race detector를 넣어 빌드한 실제 바이너리의 별도 `setup serve` 프로세스에
관리 요청을 보내 다음을 확인했다. 검사용 입력은 격리된 로컬 디렉터리에만 두었다.

- 6개 서비스 동시 자료 설치가 같은 팩 해시를 반환하고 매뉴얼 권한은 0600.
- 비동기 client 오류 처리 중 여러 상태 조회가 정상 반환.
- 동일 설정 ID 재사용, 경로 이탈 ID, 미지원 서비스, 임의 `setup.exec` 작업 거부.
- 상태 파일에 OAuth URL·client 경로·계정·조회 조건이 들어가지 않음.
- 설치된 파일을 임의 수정한 뒤 재설치 시 오류 반환, 수정 바이트 보존.
- 제어 프로세스 상태 조회와 SIGINT 종료 성공, race detector 진단 없음.
- `setup stop`으로 설정 전용 호스트 종료, 같은 명령은 보고 worker에서 거부되고
  worker가 계속 실행됨. 저장소 밖 작업 디렉터리에서 새 설정 대화도 성공했으며
  바이너리에 포함해 설치한 문서의 로컬 링크 9개를 확인했다.

## 수행한 검사와 남은 한계

- Go 빌드, `go test ./internal/runner ./internal/feedback`, 직접 영향 패키지
  `go vet ./internal/onboarding ./internal/cli ./internal/runner` 통과.
- 문서 로컬 링크 및 `git diff --check` 확인. 새로운 테스트 파일은 추가하지 않았다.
- 전체 프로젝트 테스트나 보고 실행기의 실제 모델 재실행은 하지 않았다.
  `internal/executor/codex.go`와 기존 실행기 허용 도구·권한 설정은 변경하지 않았다.
- 새 브라우저 로그인 완료/거부/시간 초과, 실제 로그인 대기 중 취소, 잘못된 Google
  계정으로 승인, Keychain 실패 후 정리의 신규 E2E 시나리오는 미검증이다.
- 만료 연결의 in-place 재인증은 기존 단독 CLI 경로에 남아 있다.
- LLM 자유대화, 외부 package 자동 설치, 나머지 5개 live adapter, 원격 쓰기,
  evaluator 격리/출시 품질 게이트, 일반 배포 패키지는 이 작업으로 완료되지 않는다.
- 설정 프로세스는 기존 호스트 권한으로 동작한다. 보고 실행기 격리의 이전 증거를
  확장된 모든 환경에 재검증한 것으로 주장하지 않는다.

현재 사용법은 [연동 안내](../setup/INTEGRATIONS.md), 실행 계약과 복구 범위는
[setup v1](../contracts/setup-v1.md)에 있다. 새 사용자 E2E 완료는 Google client
파일·계정·조회 범위와 사용자 브라우저 승인이 확보된 뒤 별도로 기록한다.
