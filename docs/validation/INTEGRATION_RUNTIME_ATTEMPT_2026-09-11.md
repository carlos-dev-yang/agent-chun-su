# 춘수 별도 실행과 대화형 설치 진입 점검

날짜: 2026-09-11. 대상 코드: `c194de9`, macOS 현재 체크아웃.
사용자 요청: 춘수를 따로 실행하고 6개 서비스를 하나씩 대화로 설치 시도하기.

## 결과

**실제 worker는 실행했지만 AI와의 설치 대화는 시작하지 못했다.** 현재 제품에는
자연어 입력을 받는 진입점과 설치 Skill을 실행기로 전달하는 경로가 없다.
따라서 이 기록은 6개 서비스 설치 성공/실패 평가가 아니라 공통 진입점의 실패 증거다.
2026-09-10 기록은 준비 도구 검증이며 실제 춘수 대화 검증이 아니었다.

## 수행 환경과 실제 관찰

현재 소스로 `go build -o bin/chunsu ./cmd/chunsu`를 실행해 성공했다.
Git에서 제외된 `var/onboard-*` 아래 새 전용 데이터 디렉터리를 만들어 기존
사용자 계정·작업·스케줄과 분리했다. `setup`은 새 SQLite schema 4를 생성했다.
발견된 Codex 실행 경로와 executor 종류만 설정했다. 모델 호출, 로그인 상태 확인,
기존 인증정보 조회, 실제 계정 복사, live 데이터 공개 승인은 하지 않았다.

아래 명령은 모두 동일한 점검용 `--home`을 지정했다.

| 단계 | 실제 입력/실행 | 관찰 |
|---|---|---|
| 실행 | 별도 PTY 프로세스에서 `worker` | 계속 실행됨. `status`가 `owner: controller`, `active_job: ""` 반환 |
| 첫 설치 요청 | worker stdin에 “구글 드라이브를 연동하고 싶어. Sheets와 Docs를 사용할 수 있도록 필요한 것을 물어보고 설치를 시작해줘.” 입력 | 터미널 입력 echo만 나타남. AI 응답·작업 생성 없음 |
| 대화 진입점 확인 | `chat '구글 드라이브 설치를 시작해줘'` | 종료 1, `unknown command "chat" for "chunsu"` |
| 작업 확인 | `--json jobs` | `[]` |
| 설치 명령 확인 | worker 종료 후 `gmail connect --help`, 이어서 인자 없는 `gmail connect` | help에는 client/account/query 플래그. 실행은 종료 1, `provide --client with the local Google Desktop app client JSON path`; 질문으로 이어지지 않음 |
| 실행 중 연결 시도 | worker 재시작 후 인자 없는 `gmail connect` | 잠금 대기 후 종료 1, `another controller owns this data directory; use its management channel or wait` |
| 종료 확인 | 점검 worker에 Ctrl-C, `status`, `--json jobs`, 연결 목록 확인 | worker 종료 0, `owner: not running`, 작업·연결 없음 |

stdin 관찰은 응답 시간을 추측해 내린 결론이 아니다. `internal/cli/run.go`의
worker는 큐와 스케줄을 처리하며 stdin을 읽지 않는다. 별도 `chat` 명령도
`internal/cli/root.go`에 등록되어 있지 않다. 두 방식에서 같은 공통 결손이
확인되어 나머지 서비스에 같은 자연어 입력을 반복하지 않았다.

## 서비스별 판정 범위

| 서비스 | 이번에 실제 시도한 것 | 아직 확인하지 못한 것 |
|---|---|---|
| Google Drive / Docs / Sheets | worker 자연어 요청, CLI 대화 진입 시도 | AI 안내, 설치, OAuth, 문서/시트 호출 모두 진입 불가 |
| Figma | 공통 명령 등록·설치 팩 연결 경로를 소스에서 확인 | 개별 대화·설치·인증 미시도 |
| GitHub | 동일 | 개별 대화·설치·인증 미시도 |
| Slack | 동일 | 개별 대화·앱 설치·인증 미시도 |
| Telegram | 동일 | 개별 대화·봇 설정·인증 미시도 |
| Gmail | 기존 연결 명령을 worker 정지/실행 상태에서 각각 호출 | 사용자 질문, OAuth 진입, 계정 확인은 수행하지 못함 |

현재 다른 5개 서비스는 native 명령이 없으며, 외부 실행기를 통해 설치를
위임하는 공통 경로도 없다. 이 사실은 개별 제공자 인증 실패와 다르다.
Gmail의 기존 연결 구현 자체가 동작하지 않는다고 판정한 것도 아니다.
이번에는 새 데이터 환경에서 누락 입력과 동시 실행의 진입 동작만 확인했다.

## 원인과 다음 구현 범위

1. **설치 대화 진입점 부재.** 사용자 메시지, 후속 답변, 취소, 설치 단계 재개를
   받는 세션이 필요하다. 기존 `resolve`는 작업 개입 기록이며 범용 대화가 아니다.
2. **설치 Skill 전달 경로 부재.** `workgroups/assets.go`는 mail/Jira만 포함하고,
   `cmd`, `internal`, `workgroups`에서 `connect-services`/`setup-skills` 참조가 없다.
   현재 보고 실행기는 host Skill 탐색을 끄고 제한된 source 도구만 주입한다.
3. **실행 중 설정 변경 경로 부재.** `gmail connect`는 직접 writer lock을 얻는다.
   worker가 소유 중일 때 설정 요청을 전달할 관리 작업이 없으므로 시작부터 막힌다.
   인증 대기를 이유로 전체 worker를 멈추거나 writer 소유권을 우회하는 방식은
   자동 채택하지 않는다. 호스트의 연결 요청 처리 방식을 먼저 정해야 한다.
4. **누락 입력이 오류로 끝남.** Gmail CLI를 대화형 설정 세션과 연결해 client 파일
   경로·계정·조회 범위를 물은 뒤 브라우저 인증으로 넘겨야 한다.

권고하는 첫 구현 범위는 [IN-01·IN-02](../implementation/INTEGRATION_ONBOARDING.md)의
설정 전용 대화 세션과 호스트 실행 경로다. 6개 매뉴얼을 같은 대화 진입점으로
선택할 수 있게 하되, 실제 설치 완료 표시는 호스트 결과가 있을 때만 한다.
Gmail을 첫 실제 연결로 검증하고 나머지는 adapter/helper가 준비되는 순서에 따라
실제 인증까지 확장한다. 보고 실행기의 shell/MCP 제한은 유지한다.

첫 완료 증거는 **worker를 켜 둔 채 새 사용자가 자연어 요청 → 추가 질문에 답변 →
인증 인계 → 실제 연결 결과 확인**까지 진행한 기록이다. 취소, 재개, 이미 연결된
계정, 인증 실패도 이어서 확인해야 한다. 준비표 출력이나 연결 설명만으로
이 완료 조건을 충족했다고 표시하지 않는다.

이 범위는 아직 구현하지 않았다. 새 설정 세션의 도구 권한과 관리 호출 형태는
AGENTS.md의 미확정 권한·인터페이스 결정에 해당하므로 별도 확인 대상이다.

## 검증 한계와 정리

- 실제 AI 설치 대화 0건, 제공자 인증/설치 완료 0건. 6개 모두 테스트했다고 하지 않는다.
- 외부 패키지 설치, OAuth 브라우저, Keychain 조회/변경, 외부 메시지·문서 쓰기 없음.
- 점검 worker 두 세션은 종료했고 로그인 시 자동 실행 서비스를 등록하지 않았다.
- 새 Go 코드·테스트 코드는 작성하지 않았다. 전체 Go 테스트는 실행하지 않았다.
- 빌드, 위 직접 실행, 변경 문서의 로컬 링크와 `git diff --check`를 확인했다.
- 점검용 DB와 로컬 빌드는 Git에서 제외하며 실제 사용자 런타임 상태로 취급하지 않는다.
